# Load Test & Reliability Hardening — 2026-10-01

A light smoke test (ramp 1→8 virtual users over 30s against public pages: `/`,
`/deals`, `/deals-v2`, `/login`) was enough to push the `web` deployment into
crash-looping — two pods failed liveness/readiness probes with timeouts and
were killed/restarted (6 and 3 times respectively) within minutes. p50 latency
was a healthy 218ms, but p99 spiked to 7.2s and ~4% of requests errored
outright. The whole stack runs on a single Contabo VPS (6 vCPU / 12GB), shared
by Postgres, Redis, Celery, the web/Django pods, and the CI runner, so there
was real headroom — the web tier just wasn't configured to use it.

---

## Root cause

| Factor | Before | Problem |
|---|---|---|
| `web` pod resources | 128Mi/100m request, 256Mi/250m limit | Far tighter than `django` (256Mi/250m req, 512Mi/500m limit) for a comparable Node.js SSR workload |
| Probe `timeoutSeconds` | unset (defaults to 1s) | A pod briefly slow under load — not actually unhealthy — gets killed anyway, which is the proximate cause of the crash-loop observed |
| HPA | `minReplicas: 2`, `maxReplicas: 4`, target 70% CPU, default scale-up stabilization (~3 min) | Scales up too slowly to get ahead of a spike; low floor means less headroom before the first signs of trouble |

A fourth hypothesis — that `/deals` and `/deals-v2` were doing expensive
per-request SSR data-fetching and should move to ISR — turned out **not** to
apply: both are `"use client"` components that fetch deal data via
`react-query` directly from the browser against the Django API. Checking the
built image's `prerender-manifest.json` confirmed both routes are already
fully static (`initialRevalidateSeconds: false`, prerendered `.html` in
`.next/server/app/`). There was no server-side rendering cost to cache away;
no code change was made here.

---

## Changes made (`k8s/07-web.yaml`)

- **Resources**: `128Mi/100m` → `256Mi/512Mi` request/limit on memory,
  `100m/250m` → `200m/500m` on CPU — brought in line with `django`'s limits.
- **Probes**: added `timeoutSeconds: 3` and `failureThreshold: 3` to both
  `readinessProbe` and `livenessProbe`, so a pod under brief load pressure
  isn't killed for responding in 1.5s instead of 1s.
- **HPA**: `minReplicas` 2→3, `maxReplicas` 4→6, CPU target 70%→60%, plus an
  explicit `behavior` block — `scaleUp` stabilization dropped to 0s with a
  100%-or-+2-pods-per-30s policy (whichever adds more), `scaleDown`
  stabilization kept at 120s so capacity doesn't flap back down mid-spike.

## Not changed

- `/deals`, `/deals-v2` — already static, nothing to convert.
- Django/Celery resources and HPA — not exercised by this test; revisit if a
  future test targets authenticated/API-heavy flows.

## Re-test

Not yet re-run against production post-fix, to avoid repeatedly stressing the
live site. Recommended before trusting these numbers under a real spike: a
second light smoke test at the same 8-VU level (should show zero probe
failures now) and, if that's clean, a moderate test (~50 concurrent users) to
find the new ceiling — during a planned low-traffic window.
